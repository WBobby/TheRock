# RFC0007 RDC TheRock 集成 - 实施分析报告

## 执行摘要

基于对当前 RDC 实施（77e4a830 之后的提交）与 RFC0007 规范的对比分析，该集成**部分完成**，但存在与 RFC 推荐方法的**重大架构偏差**。

## 当前实施状态

### 已满足的需求

#### 1. 基本集成结构

- ✅ RDC 成功集成到 TheRock 的 [`profiler/`](profiler/CMakeLists.txt) 目录下
- ✅ gRPC 已添加到 TheRock 第三方依赖，位于 [`third-party/grpc/`](third-party/grpc/CMakeLists.txt)
- ✅ 同时构建嵌入式和独立模式（rdcd 守护进程和 rdci CLI 工具）
- ✅ 所有核心 RDC 库已构建：librdc.so (610KB)、librdc_bootstrap.so (131KB)、librdc_client.so (20MB)
- ✅ 可选模块已构建：librdc_rocr.so (~320KB)、librdc_rocp.so (~320KB)

#### 2. gRPC 构建配置

- ✅ gRPC v1.76.0 已构建为**静态库**（libgrpc++.a、libgrpc.a、libprotobuf.a）
- ✅ 所有 gRPC 依赖项从子模块构建（abseil、re2、protobuf、c-ares）
- ✅ 使用 BoringSSL 作为 SSL 提供者（从 gRPC 子模块静态链接）
- ✅ 已实现静态库验证测试
- ✅ 正确设置 BUILD_SHARED_LIBS=OFF

#### 3. 实际二进制文件大小

- rdcd：**16MB**（RFC 预期 ~50MB）
- rdci：**323KB**（RFC 预期 ~50MB）  
- librdc_client.so：**20MB**（RFC 预期包含静态 gRPC 的 ~50MB）
- librdc_bootstrap.so：**131KB**（RFC 预期 ~200KB）✅
- librdc.so：**610KB**（RFC 预期 ~2MB）✅

#### 4. 依赖管理

- ✅ 使用 RUNTIME_DEPS 正确声明依赖（amdsmi、rocprofiler-sdk、ROCR-Runtime）
- ✅ 为下游消费者提供 CMake 包
- ✅ 正确的组件分离生成构件（dev、lib、run、doc、dbg）

### 关键差距：未遵循 RFC 规范

**⚠️ 重大偏差：gRPC 静态链接到二进制文件，而非共享库**

RFC 明确指出（"静态链接架构"部分）：

> 将 gRPC 静态链接到 RDC 独立组件（rdcd、rdci、librdc_client.so）

**当前实际情况：**

```bash
# rdcd 包含静态嵌入的 gRPC 符号（16MB 二进制文件）
$ nm --dynamic rdcd | grep grpc::  # 包含 gRPC 符号

# librdc_client.so 静态链接了 gRPC（20MB 库）  
$ readelf -d librdc_client.so.1.2 | grep NEEDED
# 没有 libgrpc++.so 依赖 - gRPC 已嵌入

# 未安装 gRPC 共享库
$ ls build-4/dist/rocm/lib/rdc/grpc/
# 目录不存在
```

**这为什么重要：**

1. **二进制大小更小**，低于 RFC 预期（16MB vs 50MB），表明静态链接成功
2. **没有运行时 gRPC 依赖污染** - gRPC 符号是私有的
3. **实现了可移植分发** - 不需要外部 gRPC .so 文件
4. RDC 的 CMakeLists.txt 仍有安装 gRPC 库的代码（316-352 行），但这是**死代码**，因为 `GRPC_ROOT` 检测阻止了它的执行

### 仍需改进的方面

#### 1. 符号可见性管理 ❌

**RFC 要求（231-261 行）：**

```cmake
CMAKE_ARGS
  -DCMAKE_CXX_VISIBILITY_PRESET=hidden
  -DCMAKE_C_VISIBILITY_PRESET=hidden  
  -DCMAKE_VISIBILITY_INLINES_HIDDEN=ON
```

**当前状态：** 未实施

- gRPC 构建时未使用明确的可见性控制
- librdc_client.so 中可能存在符号污染
- 风险：如果其他组件使用 gRPC/protobuf，可能导致 ODR 冲突

**证据：**

```bash
$ grep -E "VISIBILITY|visibility" third-party/grpc/CMakeLists.txt
# 无结果 - 缺少可见性标志
```

#### 2. RDC CMake 现代化 ❌

**RFC 建议（287-296 行）：**

```cmake
# 现代方法：
find_package(gRPC REQUIRED CONFIG)
# TheRock 的 CMAKE_PREFIX_PATH 处理发现过程
```

**当前状态：** 部分解决

- 仍使用传统的 `GRPC_ROOT` 变量（rdc/CMakeLists.txt 第 158 行）
- `find_package(gRPC HINTS ${GRPC_ROOT} CONFIG)` 可工作但不理想
- TheRock 正确设置了 CMAKE_PREFIX_PATH，使 GRPC_ROOT 变得多余

#### 3. RDC 中的死代码 ❌

**问题：** RDC 的 CMakeLists.txt（316-352 行）包含安装 gRPC 共享库的代码

**实际情况：** 此代码从不执行，因为：

- gRPC 是静态链接的
- `GRPC_ROOT` 指向 TheRock 的 stage 目录  
- 条件 `if(NOT GRPC_ROOT STREQUAL GRPC_ROOT_DEFAULT)` 是为 `/usr` 设计的，不适用于 TheRock

**建议：** 删除或记录此死代码路径

#### 4. 文档缺口 ❌

**缺失内容：**

- 未更新 [`docs/development/dependencies.md`](docs/development/dependencies.md) 中的 gRPC 内容
- RFC 要求将 gRPC 记录为捆绑依赖项
- 当前文档仅列出：bzip2、elfutils、libcap、libdrm、liblzma、numactl、sqlite3、zlib、zstd

#### 5. Artifact TOML 清晰度 ❌

**当前 [`profiler/artifact-rdc.toml`](profiler/artifact-rdc.toml) 第 9 行：**

```toml
[components.dev."profiler/rdc/stage"]
include = [
  "include/**",
  "lib/cmake/**",
  "lib/rdc/grpc/**",  # <-- 这个目录不存在！
]
```

`lib/rdc/grpc/**` 模式是从计划将 gRPC 作为共享库分发时遗留下来的。应该删除。

#### 6. 二进制大小优化机会

**RFC 提到（82-88 行）：**

> 未来优化：创建"瑞士军刀"式的 librdc_grpc.so

> - 将总大小从 ~150MB 减少到 ~55MB

**当前总计：** 16MB + 323KB + 20MB = ~36MB（已经优于 RFC 的"优化"目标！）

**分析：** 当前架构已经实现了出色的大小效率。"瑞士军刀"优化是不必要的。

### 阶段 4：文档化（中等优先级）

**目标：** 更新 TheRock 文档以反映 gRPC 集成

**所需更改：**

1. 更新 [`docs/development/dependencies.md`](docs/development/dependencies.md)：
```markdown
## gRPC

gRPC 仅由 RDC 的独立模式（rdcd/rdci）使用。

- **集成方式：** `third-party/grpc/` 下的第三方静态库
- **版本：** v1.76.0（RFC0007 指定 1.67.1+，为兼容性升级）
- **SSL 提供者：** BoringSSL（从 gRPC 子模块构建）
- **链接方式：** 静态链接到 RDC 二进制文件（rdcd、rdci、librdc_client.so）
- **标准方法：** `find_package(gRPC CONFIG REQUIRED)`
- **导入库：** `gRPC::grpc++`、`gRPC::grpc`、`protobuf::libprotobuf`
- **捆绑变量：** `THEROCK_BUNDLED_GRPC`（仅在 Linux 上可用）
- **替代方案：** 无（仅 RDC 独立模式需要）
```

## 总结与建议

### 当前状态评估

**评分：B+（85/100）**

- 核心功能：✅ 优秀（所有需求已满足）
- 架构：✅ 正确（静态链接工作正常）
- 文档：⚠️ 需要改进
- 代码卫生：⚠️ 存在死代码和传统模式
- 符号安全：❌ 未实施（但风险低）

### 优先级排序

1. **高优先级：** 阶段 1（符号可见性）- 防止未来的 ODR 问题
2. **中等优先级：** 阶段 4（文档化）- 帮助未来的维护者
3. **中等优先级：** 阶段 2（CMake 现代化）- 提高代码质量
4. **低优先级：** 阶段 3（死代码清理）- 锦上添花
5. **低优先级：** 阶段 5（测试）- 覆盖率已经足够

### 关键洞察

1. **RFC 是保守的：** 二进制大小比 RFC 预测小 60-70%，显示了出色的优化
2. **架构是健全的：** 静态链接工作正确，没有共享库污染
3. **风险很低：** TheRock 中只有 RDC 使用 gRPC，因此符号可见性问题在实践中不太可能发生
4. **实施有偏差但成功：** 构建不遵循 RFC 的确切 CMake 模式，但实现了所有功能目标

### 给用户的建议

**应按此顺序进行改进：**

1. 实施阶段 1（符号可见性）作为安全措施
2. 更新文档（阶段 4）以反映实际实施  
3. 如果时间允许，可选择处理阶段 2-3 以提高代码质量

**不要实施** RFC 中提到的"瑞士军刀"优化 - 当前架构已经超过了优化目标。
